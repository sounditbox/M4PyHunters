Лекция 7: SQLModel и SQLite

После L6 у нас есть Products API с валидацией, JWT, ролями и тестами. Теперь перенесём товары и пользователей в базу. Данные должны переживать перезапуск приложения. Затем свяжем товар с пользователем, который его создал.

С помощью SQLModel объединим описание общих полей Pydantic и ORM. Разберём таблицу, Engine, Session и транзакцию, затем подключим их к нашим сервисам, зависимостям и тестам.

От чего отталкиваемся

app/
├── main.py                # create_app(), /health, обработчик 404
├── core/                  # config.py, lifespan.py, security.py
├── db/                    # fake_db.py, fake_users.py
├── dependencies/          # db.py, settings.py, auth.py
├── routers/               # product.py, auth.py
├── schemas/               # product.py, auth.py
└── services/              # product.py, auth.py
tests/                     # проверки из L6

Сейчас lifespan копирует fake_db в app.state.db, а DbDep передаёт этот словарь сервису товаров. При новом запуске изменения пропадают.

Чтение товаров требует CurrentUserDep, запись — AdminUserDep. Пользователи пока хранятся в app.state.users. Во второй части лекции перенесём их в БД, сохранив вход на /auth/token.

План перехода

HTTP-запрос + JWT
        ↓
routers/product.py       проверка входа и прав
        ↓
services/product.py      получение и изменение товаров
        ↓
Session → Engine → SQLite-файл

Создадим app/models/product.py для таблицы и app/db/database.py для подключения. В существующих сервисах заменим операции со словарём на SQLModel.

Далее блоки с именем файла собираются по порядку: «заменить файл» означает весь файл, «продолжение» — дописать в конец. Небольшие замены классов указаны отдельно. Сервер и тесты запускаем после сборки всех изменений.

Что даёт SQLModel

SQLModel построен на SQLAlchemy и Pydantic. Он позволяет описывать общие поля один раз, а затем использовать их в схеме API и в модели таблицы. Для запросов есть удобный Session.exec().

ПонятиеРоль
SQLModel без table=TrueМодель данных с проверками Pydantic; таблицу не создаёт.
SQLModel с table=TrueМодель таблицы, с которой работает ORM SQLAlchemy.
ORMСвязывает строки таблицы с Python-объектами.
EngineЗнает адрес базы, драйвер и управляет соединениями.
SessionВыполняет запросы и отслеживает изменения объектов.
ДрайверПередаёт SQL базе. Для SQLite это встроенный sqlite3.

SQLModel сокращает часть кода, но не отменяет SQLAlchemy: соединения, SQL-выражения и транзакции работают на его основе. Выбираем библиотеку по удобству для проекта, а не по возрасту; автоматического ускорения от замены нет.

Установка и настройки

uv add sqlmodel

SQLAlchemy и Pydantic установятся как зависимости. Отдельный сервер и дополнительный драйвер для SQLite не нужны.

Лекцию собираем от состояния после L6. Если уже выполняли предыдущий вариант L7, сначала уберите добавленную там прямую зависимость командой uv remove sqlalchemy, затем установите SQLModel. В итоговом варианте отдельный app/models/base.py не используется.

В app/core/config.py добавляем одно поле внутрь существующего Settings:

    database_url: str = "sqlite+pysqlite:///./products.db"

Остальные настройки, ограничения паролей и ключа, model_config и get_settings() сохраняем.

В .env и .env.example добавляем:

DATABASE_URL=sqlite+pysqlite:///./products.db

Это относительный путь: запускаем команды из корня проекта. Файл products.db появится при создании таблиц. В .gitignore добавляем *.db и *.db-*.

Схемы данных

В app/schemas/product.py импортируем SQLModel из sqlmodel и заменяем родителя BaseModel на SQLModel; ProductCreate и ProductRead продолжают наследоваться от ProductBase, поля, настройки и валидаторы сохраняем.

Поле specs: ProductSpecs | None = None переносим из ProductBase в оба класса ProductCreate и ProductRead: в API это вложенная модель, а в таблице ниже будет JSON-словарь.

Все схемы здесь без table=True. Field оставляем из Pydantic. В SQLModel уже включено from_attributes=True: схема читает поля прямо из ORM-объекта, поэтому для ответа достаточно response_model=ProductRead, без ручной сборки словаря.

Модель таблицы товара

Создаём пакет app/models/ с пустым __init__.py.

Новый app/models/product.py целиком:

from sqlalchemy import Column, JSON
from sqlmodel import Field

from app.schemas.product import CategoryName, ProductBase


class Product(ProductBase, table=True):
    __tablename__ = "products"

    id: int | None = Field(default=None, primary_key=True)
    category: CategoryName = Field(index=True)
    specs: dict | None = Field(
        default=None, sa_column=Column(JSON(none_as_null=True), nullable=True),
    )

table=True превращает модель в описание таблицы. SQLModel.metadata собирает такие таблицы; собственный DeclarativeBase не нужен.

Здесь Field импортирован из SQLModel: он умеет задавать первичный ключ, индекс и sa_column. Для JSON используем тип SQLAlchemy — это обычный способ уточнить настройки SQLModel.

Параметры Field для таблиц

В классе с table=True у Field из SQLModel есть дополнительные аргументы, которые настраивают столбец в базе:

АргументЧто задаёт в БД
primary_key=TrueПервичный ключ: идентификатор строки, как наш id.
index=TrueИндекс для поиска и фильтрации, как у category. Ускоряет подходящие запросы, но занимает место и усложняет запись.
unique=TrueЗапрещает повторяющиеся значения, например одинаковые логины.
nullable=FalseЗапрещает SQL NULL в столбце независимо от того, как данные попали в БД.
foreign_key="users.id"Внешний ключ на другую таблицу. Ниже свяжем товар с пользователем через такой ключ.
sa_type=...Явный SQL-тип, если автоматический вывод из Python-типа не подходит.
sa_column=Column(...)Готовое описание столбца SQLAlchemy, как у нашего JSON-поля specs.
sa_column_kwargs={...}Дополнительные аргументы для Column, например {"server_default": "0"} — default на стороне БД, который работает и при записи другими клиентами.

Если передаём готовый sa_column=Column(...), его nullable, index и другие настройки задаём внутри Column, а не повторяем в Field.

Типы и ограничения: что важно для нашего API

price и sale_price у нас имеют тип float, SQLModel создаёт соответствующие столбцы. Сохраняем текущие схемы и числовой JSON. Для точных денежных расчётов обычно выбирают целые минимальные единицы или Decimal и Numeric; такой переход потребует согласованно изменить схемы и тесты.

specs сохраняем как JSON: model_dump(mode="json") превратит ProductSpecs во вложенный словарь. none_as_null=True сохраняет Python None как SQL NULL.

Проверки min_length, gt и наших валидаторов работают при валидации данных. Они не превращаются автоматически в CHECK-ограничения базы. SQLite также не ограничивает длину строки только по размеру VARCHAR.

Engine: подключение к базе

Новый app/db/database.py целиком:

from sqlalchemy import Engine
from sqlmodel import create_engine


def create_database_engine(database_url: str) -> Engine:
    options = {}
    if database_url.startswith("sqlite"):
        options["connect_args"] = {"check_same_thread": False}
    return create_engine(database_url, **options)

Engine создаём один раз на запуск приложения. Это Engine SQLAlchemy, поэтому его тип импортирован оттуда. Сессии будем создавать через sqlmodel.Session(engine) прямо в зависимости.

check_same_thread=False разрешает SQLite-соединению использоваться последовательно из разных потоков FastAPI. Это не разрешение выполнять параллельные операции с одной Session.

Подключаем базу в lifespan

Заменяем app/core/lifespan.py целиком:

import logging
from contextlib import asynccontextmanager
from copy import deepcopy

from fastapi import FastAPI
from sqlmodel import SQLModel

from app.core.logging_conf import configure_logging
from app.db.database import create_database_engine
from app.db.fake_users import fake_users
from app.models.product import Product  # регистрирует таблицу в metadata

logger = logging.getLogger("lifespan")


@asynccontextmanager
async def lifespan(app: FastAPI):
    configure_logging()
    logger.info("App starting up...")
    engine = create_database_engine(app.state.settings.database_url)
    try:
        SQLModel.metadata.create_all(engine)
        app.state.engine = engine
        app.state.users = deepcopy(fake_users)
        yield
    finally:
        engine.dispose()
        logger.info("App shutting down...")

app.state.settings зададим в create_app() ниже. Импорт Product нужен до create_all(), даже если имя не используется в теле функции.

app.state.db больше не создаём. dispose() освобождает соединения при завершении. Пользователей, логирование и обработку JWT сохраняем.

Таблица и начальные данные — разные вещи

create_all() создаёт отсутствующие таблицы. Повторный запуск не очищает товары и не заполняет таблицу заново.

Первый запуск с новым products.db даст пустой список и products_count: 0. Товары создадим через API. Пять записей из fake_db будем добавлять явно в тестах.

create_all() не добавит новый столбец в уже существующую таблицу и не хранит историю изменений схемы. Для этого в L8 подключим Alembic.

В app/db/fake_db.py сохраняем словарь для тестов, а старую функцию get_db() и импорт Request удаляем.

Одна Session на запрос

Заменяем app/dependencies/db.py целиком:

from collections.abc import Iterator
from typing import Annotated

from fastapi import Depends, Request
from sqlmodel import Session

from app.db.fake_users import get_users
from app.schemas.auth import UserInDB

UsersDep = Annotated[dict[str, UserInDB], Depends(get_users)]


def get_session(request: Request) -> Iterator[Session]:
    with Session(request.app.state.engine) as session:
        try:
            yield session
        except Exception:
            session.rollback()
            raise


SessionDep = Annotated[Session, Depends(get_session)]

До yield создаём сессию, после выполнения запроса выходим из with и закрываем её. При ошибке откатываем текущую транзакцию и передаём исключение дальше.

Импортируем именно Session из SQLModel: у неё есть метод exec(). Commit по умолчанию помечает поля для перечитывания; перед ответом явно вызываем refresh(), пока сессия открыта.

UsersDep остаётся нужен авторизации. Глобальную Session не создаём. Закрытие сессии само по себе не фиксирует изменения.

Как устроен запрос на чтение

from sqlmodel import select

statement = (
    select(Product)
    .where(Product.price < 100)
    .order_by(Product.id)
    .limit(10)
)
products = session.exec(statement).all()

select() строит описание запроса. where(), order_by() и limit() возвращают новую версию этого описания. Запрос выполняется при обращении к Session.

SQLAlchemy переводит выражение в SQL нужной базы, драйвер передаёт SQL и параметры, а ORM собирает объекты Product из результата.

Атрибуты класса перегружают операторы: Product.price < 100 строит SQL-условие. Для нескольких условий используем несколько where(), and_() или or_(), а не Python and/or.

Как получить результат

ВызовРезультат
session.get(Product, 1)Объект по первичному ключу либо None.
session.exec(select(Product)).all()Список объектов Product.
session.exec(select(Product.name, Product.price)).all()Строки с несколькими выбранными значениями.
session.exec(select(func.count()).select_from(Product)).one()Одно число — количество товаров.

select импортируем из sqlmodel. Для одной выбранной сущности exec() уже возвращает результат без обёртки строки — дополнительный scalars() не нужен. Для нескольких столбцов получаем строки.

first() возвращает первый результат или None; one() требует ровно один, one_or_none() — не больше одного. У COUNT без группировки одна строка даже для пустой таблицы: её значение 0.

Внутри Session один товар с одним ID представлен одним ORM-объектом — это identity map. get() может использовать уже загруженный объект, но Session не является общим кэшем всех запросов.

Чтение одного товара и списка

В app/services/product.py добавляем импорты from sqlmodel import Session, col, select и from app.models.product import Product. Классы ServiceError и ProductNotFoundError сохраняем; далее заменяем одноимённые функции.

def get_product_by_id(product_id: int, db: Session) -> Product:
    product = db.get(Product, product_id)
    if product is None:
        raise ProductNotFoundError
    return product


def get_products(
    search: str | None, limit: int, category: str | None,
    only_available: bool, db: Session,
) -> list[Product]:
    statement = select(Product)
    if only_available:
        statement = statement.where(col(Product.is_available).is_(True))
    if category:
        statement = statement.where(Product.category == category)
    if search:
        statement = statement.where(
            col(Product.name).icontains(search, autoescape=True)
        )
    statement = statement.order_by(Product.id).limit(limit)
    return list(db.exec(statement).all())

Сохраняем параметры и их порядок, включая only_available=True в роутере. order_by(Product.id) обеспечивает определённый порядок, важный и для лимита, и для тестов.

col() из SQLModel помогает редактору понять, что здесь используется SQL-столбец с методами is_() и icontains(), а не обычный Python bool или str.

icontains() ищет подстроку без учёта регистра, autoescape=True делает символы % и _ обычными символами поиска. В стандартной SQLite преобразование регистра ограничено ASCII: поиск кириллицы с разным регистром потребует отдельного решения.

Значения передаём параметрами

statement = select(Product).where(Product.category == category)

Значение category отправляется отдельно от SQL-кода. Не склеиваем SQL с пользовательским вводом через f-строки.

Когда нужен ручной SQL, используем text() и параметры:

from sqlalchemy import text

rows = session.execute(
    text("SELECT name, price FROM products WHERE category = :category"),
    {"category": category},
).all()

В нашем CRUD достаточно ORM. Для сложных запросов также существуют join(), offset(), func.sum() и выражения insert(), update(), delete().

Создание товара и сохранение

В app/services/product.py добавляем product_values() и заменяем create():

def product_values(data: ProductCreate) -> dict:
    return data.model_dump(
        mode="json", include=set(ProductCreate.model_fields),
    )


def create(product: ProductCreate, db: Session) -> Product:
    saved = Product.model_validate(product_values(product))
    db.add(saved)
    db.commit()
    db.refresh(saved)
    return saved

add() добавляет объект в сессию, commit() фиксирует изменения, refresh() перечитывает запись. ID назначает SQLite.

У ProductCreate разрешены extra-поля. Через include берём только объявленные поля: присланный клиентом id не попадёт в таблицу. mode="json" превращает вложенные specs в словарь.

Сессия из нашей зависимости откатит незафиксированные изменения при исключении. Уже выполненный commit() откатить нельзя.

Полная замена и удаление

В app/services/product.py заменяем две функции:

def replace(product_id: int, to_replace: ProductCreate,
            db: Session) -> Product:
    product = get_product_by_id(product_id, db)
    product.sqlmodel_update(product_values(to_replace))
    db.commit()
    db.refresh(product)
    return product


def delete(product_id: int, db: Session) -> None:
    product = get_product_by_id(product_id, db)
    db.delete(product)
    db.commit()

sqlmodel_update() переносит проверенные значения в существующий ORM-объект. Session замечает изменения и сохраняет их при commit(). ID товара остаётся прежним.

PUT заменяет все поля: пропущенные необязательные получают значения по умолчанию. specs присваиваем новым словарём целиком. DELETE сохраняет прежний контракт: 204 с пустым телом, отсутствующий товар даёт 404.

Частичное обновление: PATCH

В app/services/product.py добавляем from pydantic import ValidationError, класс ошибки и новую функцию:

class InvalidProductDataError(ServiceError):
    def __init__(self, errors: list[dict]):
        super().__init__("Invalid product data")
        self.errors = errors


def update(product_id: int, to_update: ProductUpdate,
           db: Session) -> Product:
    product = get_product_by_id(product_id, db)
    patch = to_update.model_dump(exclude_unset=True)
    try:
        validated = ProductCreate.model_validate(product, update=patch)
    except ValidationError as exc:
        raise InvalidProductDataError(
            exc.errors(include_context=False)
        ) from exc
    product.sqlmodel_update(product_values(validated))
    db.commit()
    db.refresh(product)
    return product

exclude_unset=True берёт только присланные поля. model_validate(..., update=patch) проверяет итоговое состояние до изменения товара. SQLModel умеет читать атрибуты ORM-объекта.

Пример: у товара цена 100 и скидочная цена 80. PATCH с ценой 70 должен дать 422 и сохранить прежние значения. Явный description=null очищает описание, price=null отклоняется.

Сохраняем текущие пять полей ProductUpdate. specs и sale_price пока задаём через POST/PUT.

Подключение CRUD к API

В app/routers/product.py у всех шести эндпоинтов заменяем DbDep на SessionDep, а async def на def. Пути, параметры, response_model и зависимости прав оставляем прежними. Например:

@router.post("", response_model=ProductRead, status_code=201)
def create_product(product: ProductCreate, db: SessionDep,
                   _admin: AdminUserDep):
    return create(product, db)

Синхронную Session используем в обычных def: FastAPI выполнит обработчик в пуле потоков. Прямой вызов синхронной БД из async def блокирует цикл событий.

В app/main.py импортируем InvalidProductDataError из app.services.product, а jsonable_encoder из fastapi.encoders. Внутри create_app(), рядом с прежним обработчиком 404, добавляем:

    @app.exception_handler(InvalidProductDataError)
    async def invalid_product_data(request, exc):
        errors = [dict(e, loc=["body", *e["loc"]]) for e in exc.errors]
        return JSONResponse(
            status_code=422,
            content={"detail": jsonable_encoder(errors)},
        )

FastAPI сам обрабатывает ошибки входной схемы. Здесь превращаем ошибку ручной проверки PATCH в такой же HTTP 422.

Настройки приложения и /health

В app/dependencies/settings.py зависимость читает настройки текущего приложения:

from typing import Annotated

В app/main.py добавляем Settings к импорту из app.core.config, импортируем SessionDep из app.dependencies.db, Product из app.models.product и func, select из SQLModel. В фабрике меняем сигнатуру и настройки, затем заменяем health():

def create_app(settings: Settings | None = None) -> FastAPI:
    settings = settings if settings is not None else get_settings()
    # Существующий app = FastAPI(..., lifespan=lifespan, ...) сохраняем.

    app.state.settings = settings

Это фрагмент фабрики: подключение роутеров, оба обработчика ошибок, return app и app = create_app() сохраняем. Lifespan и JWT используют один объект настроек. Тесты смогут передать адрес отдельной БД.

Пользователь как таблица

Новый app/models/user.py целиком:

from sqlmodel import Field, SQLModel


class User(SQLModel, table=True):
    __tablename__ = "users"

    id: int | None = Field(default=None, primary_key=True)
    username: str = Field(index=True, unique=True, max_length=50)
    hashed_password: str
    role: str = "user"
    disabled: bool = False

В app/schemas/auth.py добавляем импорты Field, SecretStr из Pydantic и схему создания. Прежние UserRead и Token сохраняем:

class UserCreate(BaseModel):
    username: str = Field(min_length=3, max_length=50,
                          pattern=r"^[A-Za-z0-9_-]+$")
    password: SecretStr = Field(min_length=8)

unique=True запрещает одинаковые логины на уровне БД. В таблице храним хэш, в UserRead его нет. SecretStr скрывает пароль при обычном выводе модели, но хэш вычисляем отдельно.

В схеме создания нет поля role: через API новый пользователь получает обычную роль.

Добавление пользователя в БД

Заменяем app/services/auth.py целиком. Общая функция создания пригодится и начальному заполнению, и API:

from sqlalchemy.exc import IntegrityError
from sqlmodel import Session, select
from app.core.security import DUMMY_HASH, hash_password, verify_password
from app.models.user import User


class UsernameTakenError(ValueError):
    pass


def get_user_by_username(db: Session, username: str) -> User | None:
    return db.exec(select(User).where(User.username == username)).first()


def create_user(db: Session, username: str, password: str,
                role: str = "user") -> User:
    user = User(username=username, hashed_password=hash_password(password),
                role=role)
    db.add(user)
    try:
        db.commit()
    except IntegrityError as exc:
        db.rollback()
        raise UsernameTakenError(username) from exc
    db.refresh(user)
    return user


def authenticate_user(db: Session, username: str, password: str) -> User | None:
    user = get_user_by_username(db, username)
    valid = verify_password(password, user.hashed_password if user else DUMMY_HASH)
    return user if user is not None and valid else None

Повторный логин нарушает уникальность username. Сначала откатываем неудачную транзакцию, затем передаём понятную ошибку роутеру. При неизвестном логине сохраняем проверку фиктивного хэша из L5.

СвязьПримерКак хранить
Один ко многим, 1:NОдин пользователь создал много товаров. У товара один автор.products.created_by_id ссылается на users.id.
Один к одному, 1:1Один пользователь имеет один профиль.Внешний ключ profiles.user_id с ограничением unique=True.

Реализуем 1:N. В строках товаров храним ID автора. Несколько товаров могут ссылаться на одного пользователя:

products.idnamecreated_by_id

Внешний ключ связывает строки в БД. Relationship позволяет получать связанные Python-объекты: product.created_by и user.products.

Внешний ключ и Relationship

В app/models/product.py добавляем импорты и поля внутрь существующего Product:

from typing import TYPE_CHECKING, Optional
from sqlmodel import Relationship

if TYPE_CHECKING:
    from app.models.user import User

# Внутри class Product(...):
    created_by_id: int | None = Field(default=None, foreign_key="users.id")
    created_by: Optional["User"] = Relationship(back_populates="products")

В app/models/user.py добавляем вторую сторону:

from typing import TYPE_CHECKING
from sqlmodel import Relationship

if TYPE_CHECKING:
    from app.models.product import Product

# Внутри class User(...):
    products: list["Product"] = Relationship(back_populates="created_by")

back_populates указывает имя атрибута на другой стороне. created_by_id создаёт столбец, а created_by и products описывают доступ к объектам. Список товаров отдельным столбцом не хранится.

TYPE_CHECKING помогает избежать циклического импорта. При запуске обе модели всё равно импортирует lifespan. Разрешаем автору быть None, чтобы старые товары и тестовые данные оставались допустимыми.

Если таблица products уже существует, create_all() не добавит столбец. Для упражнения используем новый файл DATABASE_URL=sqlite+pysqlite:///./lesson7.db. Изменение существующей схемы разберём с Alembic в L8.

Чтобы SQLite проверяла внешние ключи, в create_database_engine() вместо прямого return create_engine(...) добавляем (импорт event из SQLAlchemy):

    engine = create_engine(database_url, **options)

        @event.listens_for(engine, "connect")
        def enable_foreign_keys(connection, _):
            connection.execute("PRAGMA foreign_keys=ON").close()
    return engine

Обработчик включает проверку для каждого нового соединения. SQLAlchemy: внешние ключи SQLite.
