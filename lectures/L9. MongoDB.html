Лекция 9: MongoDB для расширенных характеристик товаров

Добавим MongoDB для расширенных характеристик. Читаем их вместе с товаром, изменяем отдельными PUT, PATCH и DELETE.

Товары и пользователи остаются в PostgreSQL. Используем прежние JWT, роли и слои: router → service → хранилище; данные проверяют schemas.

Зачем здесь документная база

Общие характеристики — вес, цвет, теги — уже хранятся в SQL JSON-поле Product.specs.

У клавиатуры есть layout и switch, у монитора — refresh_rate и panel. Эти разные наборы полей сохраним отдельными документами в MongoDB.

Оставляем в SQLДобавляем в MongoDB
id, name, category, price, sale_priceХарактеристики конкретной категории: layout, switch, refresh_rate.
is_available, stock_count после L8Время создания и изменения документа характеристик.
specs: weight_grams, color, tagsНе дублируем общие specs во второй базе.
users и created_by_idproduct_id как ссылка уровня приложения.

SQL JSON тоже подходит для этой задачи. Здесь изучаем документную модель и работу с двумя базами.

Основные понятия MongoDB

ПонятиеВ проекте
Databaseproducts: пространство коллекций.
Collectionproduct_attributes: документы одного назначения.
DocumentНабор расширенных характеристик одного товара.
BSONФормат хранения с типами ObjectId, datetime, числами и вложенными объектами.
_idУникальный идентификатор документа; в нашем случае ObjectId.

MongoDB — документная NoSQL-база. Другие модели NoSQL: key-value и graph. Гибкую структуру документов ограничим схемами API и индексами.

Документ расширенных характеристик

{
  "_id": {"$oid": "6697bbef47e2631f1492be5a"},
  "product_id": 42,
  "attributes": {
    "layout": "ANSI",
    "switch": "brown",
    "wireless": false
  },
  "created_at": {"$date": "2026-11-02T12:00:00Z"},
  "updated_at": {"$date": "2026-11-02T12:00:00Z"}
}

Это Extended JSON: $oid представляет ObjectId, $date — дату BSON. В Python получим ObjectId и datetime. PUT/PATCH возвращают строковый id документа и даты ISO 8601; GET товара включает только attributes.

Один товар — один документ. Связь с SQL-товаром проверяет API: FOREIGN KEY между базами нет.

Embedding и reference

PostgreSQL                              MongoDB
users ── products.created_by_id          product_attributes
         products.id = 42  ···········>   product_id = 42
                                         attributes = {...}

Reference: product_id ссылается на SQL-товар. Embedding: attributes встроен в документ, поскольку характеристики читаются вместе. Цену, название и данные пользователя не дублируем.

CRUD в mongosh

Сначала откройте mongosh из терминала проекта:

docker compose exec mongo mongosh -u mongo -p mongo --authenticationDatabase admin

Далее работаем внутри mongosh, в отдельной учебной базе:

use products_playground

db.product_attributes.insertOne({
  product_id: 42,
  attributes: {layout: "ANSI", wireless: false}
})

db.product_attributes.findOne({product_id: 42})

db.product_attributes.updateOne(
  {product_id: 42},
  {$set: {"attributes.wireless": true}}
)

db.product_attributes.deleteOne({product_id: 42})

Первый аргумент — фильтр, второй — изменение. $set задаёт значение, точка в пути обращается к вложенному полю. Учебные документы не попадают в базу API.

Фильтр и выбор полей

db.product_attributes.insertOne({
  product_id: 43,
  attributes: {refresh_rate: 144, panel: "IPS"}
})

db.product_attributes.find(
  {"attributes.refresh_rate": {$gte: 120}},
  {_id: 0, product_id: 1, "attributes.refresh_rate": 1}
).sort({"attributes.refresh_rate": -1}).limit(10)

db.product_attributes.updateOne(
  {product_id: 43},
  {$unset: {"attributes.panel": ""}}
)

$gte: 120 — не меньше 120. Второй аргумент find — projection: 1 включает поле, _id: 0 скрывает id. В sort -1 задаёт убывание, limit(10) — до 10 документов.

$unset удаляет поле, $inc увеличивает число. В API фильтры строим сами: произвольные Mongo-операторы от клиента не принимаем.

Уникальный индекс: один товар — один документ

app/db/mongodb.py — новый файл

from pymongo.asynchronous.database import AsyncDatabase


async def ensure_product_attribute_indexes(database: AsyncDatabase) -> None:
    await database["product_attributes"].create_index(
        "product_id", unique=True, name="uq_product_attributes_product_id",

Два запроса могут одновременно выполнить find и не найти документ. Только unique=True запрещает дубли в базе. Если дубли уже есть, индекс не создастся.

В учебном приложении создаём индекс при старте, в рабочем — отдельным этапом. Alembic управляет только SQL.

Один клиент внутри lifespan

Добавляем Mongo-клиент к SQL Engine. Таблицы по-прежнему готовит Alembic; create_all не вызываем.

app/core/lifespan.py — заменить файл

import logging
from contextlib import asynccontextmanager

from fastapi import FastAPI
from pymongo import AsyncMongoClient
from sqlmodel import Session

from app.core.logging_conf import configure_logging
from app.db.bootstrap import seed_users
from app.db.database import create_database_engine
from app.db.mongodb import ensure_product_attribute_indexes

logger = logging.getLogger("lifespan")


@asynccontextmanager
async def lifespan(app: FastAPI):
    settings = app.state.settings
    configure_logging()
    logger.info("App starting up...")
    engine = create_database_engine(settings.database_url)
    mongo_client = None
    app.state.engine = engine
    app.state.mongo_database = None
    try:
        if settings.debug:
            with Session(engine) as db:
                seed_users(db, settings)

        if settings.mongodb_url is not None:
            mongo_client = AsyncMongoClient(
                settings.mongodb_url, tz_aware=True,
                serverSelectionTimeoutMS=3000,
            )
            await mongo_client.admin.command("ping")
            database = mongo_client[settings.mongodb_database]
            await ensure_product_attribute_indexes(database)
            app.state.mongo_database = database
        yield
    finally:
        try:
            if mongo_client is not None:
                await mongo_client.close()
        finally:
            engine.dispose()
    logger.info("App shutting down...")

Один клиент на lifespan: он управляет пулом соединений и работает в одном event loop. Закрываем его через await close(). tz_aware=True сохраняет информацию о часовом поясе.

Нет URL — приложение стартует без Mongo; составное чтение недоступно. URL задан, но ping или создание индекса не прошли — запуск прерывается. HTTP-обработчики не перехватывают ошибки запуска.

Проверяем входные данные

app/schemas/product_attributes.py — новый файл

from datetime import datetime
from typing import Annotated

from pydantic import (
    BaseModel, ConfigDict, Field, StrictBool, StrictFloat, StrictInt,
    StrictStr, field_validator,
)

from app.schemas.product import ProductRead

AttributeKey = Annotated[
    str, Field(pattern=r"^[a-z][a-z0-9_]{0,39}$"),
]
AttributeValue = StrictStr | StrictInt | StrictFloat | StrictBool


class ProductAttributesPut(BaseModel):
    model_config = ConfigDict(extra="forbid", allow_inf_nan=False)
    attributes: dict[AttributeKey, AttributeValue] = Field(
        min_length=1, max_length=50,
    )

    @field_validator("attributes")
    @classmethod
    def validate_attributes(cls, value):
        if {"weight_grams", "color", "tags"} & value.keys():
            raise ValueError("Общие характеристики изменяются через Product.specs")
        for item in value.values():
            if isinstance(item, str) and len(item) > 200:
                raise ValueError("Значение характеристики длиннее 200 символов")
            if type(item) is int and not -(2**63) <= item < 2**63:
                raise ValueError("Целое число не помещается в BSON int64")
        return value

Ключи: буква, затем буквы, цифры или _, до 40 символов. Значения: строка до 200 символов, целое BSON int64, конечное число или bool. Strict-типы не превращают строки в числа.

Принимаем 1–50 ключей за запрос. Запрещены вложенные объекты, списки, null и общие характеристики из Product.specs.

Схемы PATCH и ответа

app/schemas/product_attributes.py — продолжение файла

class ProductAttributesPatch(ProductAttributesPut):
    pass


class ProductAttributesRead(BaseModel):
    id: str
    product_id: int
    attributes: dict[AttributeKey, AttributeValue]
    created_at: datetime
    updated_at: datetime


class ProductWithAttributesRead(ProductRead):
    attributes: dict[AttributeKey, AttributeValue] | None = None

PATCH проверяет вход так же, как PUT. Ответ записи ProductAttributesRead содержит id документа и даты. Обычные GET используют ProductWithAttributesRead: поля товара плюс attributes.

Лимит 50 — на запрос: несколько PATCH могут накопить больше ключей. Лимит всего документа требует отдельной проверки, поэтому в схеме ответа его нет.

Чтение вместе с товаром

Клиент получает товар и характеристики одним HTTP-запросом. API объединяет данные PostgreSQL и MongoDB.

Метод и путьПраваРезультат
GET /products/{id}Активный пользовательТовар с attributes — 200; нет товара — 404.
GET /productsАктивный пользовательСписок товаров с attributes.
PUT /products/{id}/attributesadminСоздать или заменить attributes — 200.
PATCH /products/{id}/attributesadminИзменить ключи — 200; нет документа — 404.
DELETE /products/{id}/attributesadminУдалить документ — 204; нет документа — 404.

Нет документа — attributes: null. Mongo недоступна — 503. Отдельного GET /attributes нет. Запись характеристик требует существующего SQL-товара.

PUT сохраняет _id и created_at, обновляет updated_at. PATCH не удаляет ключи через null. SQL-товар эти операции не меняют.

Сервис: ошибки и преобразование BSON

app/services/product_attributes.py — новый файл

from datetime import UTC, datetime
from typing import Any, Mapping

from pymongo import ReturnDocument
from pymongo.asynchronous.database import AsyncDatabase
from pymongo.errors import DuplicateKeyError

from app.schemas.product import ProductRead
from app.schemas.product_attributes import (
    ProductAttributesPatch, ProductAttributesPut, ProductAttributesRead,
    ProductWithAttributesRead,
)


class ProductAttributesNotFoundError(Exception):
    pass


class ProductAttributesConflictError(Exception):
    pass


def attributes_to_read(document: Mapping[str, Any]) -> ProductAttributesRead:
    payload = dict(document)
    payload["id"] = str(payload.pop("_id"))
    return ProductAttributesRead.model_validate(payload)

Преобразуем ObjectId в строку и проверяем ответ схемой. Сервис отвечает за данные; HTTP-коды назначают обработчики ошибок.

Сервис: PUT через атомарный upsert

app/services/product_attributes.py — продолжение файла

async def put_attributes(
    product_id: int, payload: ProductAttributesPut, database: AsyncDatabase,
) -> ProductAttributesRead:
    now = datetime.now(UTC)
    collection = database["product_attributes"]
    query = {"product_id": product_id}
    changes = {
        "$set": {"attributes": payload.attributes, "updated_at": now},
        "$setOnInsert": {"created_at": now},
    }
    try:
        document = await collection.find_one_and_update(
            query, changes, upsert=True, return_document=ReturnDocument.AFTER,
        )
    except DuplicateKeyError:
        # Другой запрос успел первым создать документ с тем же product_id.
        document = await collection.find_one_and_update(
            query, changes, upsert=False, return_document=ReturnDocument.AFTER,
        )
    if document is None:
        # Между конфликтом вставки и повтором документ могли удалить.
        raise ProductAttributesConflictError
    return attributes_to_read(document)
  • upsert=True создаёт документ при отсутствии; product_id берётся из фильтра.
  • $setOnInsert задаёт created_at только при создании.
  • ReturnDocument.AFTER возвращает изменённый документ.

При конфликте первых PUT повторяем обновление. Если документ успели удалить — 409. При замене одного значения побеждает более поздняя запись; проверки версий здесь нет.

Объединяем товар и характеристики

app/services/product_attributes.py — продолжение файла

async def add_attributes(
    products: list[ProductRead], database: AsyncDatabase,
) -> list[ProductWithAttributesRead]:
    if not products:
        return []
    cursor = database["product_attributes"].find(
        {"product_id": {"$in": [product.id for product in products]}},
        {"_id": 0, "product_id": 1, "attributes": 1},
    )
    by_id = {
        document["product_id"]: document["attributes"]
        async for document in cursor
    }
    return [
        ProductWithAttributesRead(
            **product.model_dump(), attributes=by_id.get(product.id),
        )
        for product in products
    ]

Одна выборка $in получает характеристики всех товаров. find() возвращает курсор без await; читаем его через async for. Порядок SQL-товаров сохраняется.

Функция подходит и для одного товара. Не делаем отдельный Mongo-запрос на каждый элемент списка — это проблема N+1.

Сервис: частичное обновление

app/services/product_attributes.py — продолжение файла

async def patch_attributes(
    product_id: int, payload: ProductAttributesPatch, database: AsyncDatabase,
) -> ProductAttributesRead:
    changes = {
        f"attributes.{key}": value
        for key, value in payload.attributes.items()
    }
    changes["updated_at"] = datetime.now(UTC)
    document = await database["product_attributes"].find_one_and_update(
        {"product_id": product_id}, {"$set": changes},
        return_document=ReturnDocument.AFTER,
    )
    if document is None:
        raise ProductAttributesNotFoundError
    return attributes_to_read(document)

PUT: $set: {"attributes": ...} заменяет объект целиком. PATCH: $set: {"attributes.wireless": true} меняет один ключ.

Изменяем пути без чтения и перезаписи всего объекта: параллельные PATCH разных ключей не затирают друг друга. Без upsert отсутствующий документ даёт 404.

    payload: ProductAttributesPut,
    _admin: AdminUserDep,
    product_id: ExistingProductIdDep,
    database: MongoDatabaseDep,
) -> ProductAttributesRead:
    return await put_attributes(product_id, payload, database)

ExistingProductIdDep проверяет пользователя и SQL-товар. Для записи дополнительно нужен AdminUserDep. Сервис вызываем через await.

Атомарность: один документ

find_one_and_update атомарно меняет один документ. Для нашего CRUD этого достаточно.

Транзакции нескольких Mongo-документов требуют replica set или sharded cluster. Одиночный контейнер из лекции их не предоставляет.

Общей транзакции PostgreSQL + MongoDB нет. Откат SQL не отменяет запись в MongoDB.

Если SQL-товар удалили

Запрос A: проверил SQL-товар — существует
Запрос B: удалил SQL-товар
Запрос A: записал Mongo-документ — ссылка осталась без товара

Проверка API не исключает гонку. Mongo-документ не удалится автоматически; Alembic этим не управляет.

На практике сначала удаляем attributes, затем товар. При сбое это не даёт атомарной гарантии.

Для рабочего проекта: события и идентификаторы

Один из вариантов — SQL outbox: событие удаления записывается в одной транзакции с удалением товара, обработчик повторяемо очищает MongoDB. Брокера без надёжной записи события недостаточно.

Обычный SQL DELETE не сбрасывает sequence; после переноса мы выставили её за максимальный id. Но сброс sequence, TRUNCATE RESTART IDENTITY или восстановление только одной базы могут повторно использовать id. Нужны очистка старых документов и стабильная идентичность, например UUID; сам UUID не решает удаление.

Служебные id нельзя менять через JSON. В текущем ProductCreate стоит extra="allow": перед рабочим использованием запретите служебные поля или ограничьте поля, переносимые в ORM.

СитуацияОжидаемое поведение
mongodb_url=NoneСоставные GET товара и списка требуют Mongo — 503. SQL-запись и /health работают. Без токена — 401; нет SQL-товара — 404.

Объединённый GET зависит от двух баз. null означает отсутствие документа, а не отказ MongoDB. /health проверяет только SQL; для обеих баз нужна readiness-проверка.

Практика и результат

  1. Добавьте mongo в существующий compose.yaml, сохранив PostgreSQL и его том. Поднимите оба сервера с --wait.
  2. Сохраните PostgreSQL DATABASE_URL, добавьте два Mongo-поля Settings и unique index по product_id.
  3. Подключите AsyncMongoClient в существующий lifespan, сохранив SQL Engine, seed_users и очистку ресурсов.
  4. Создайте схемы, зависимости, сервис, router и обработчики ошибок по блокам выше.
  5. Проверьте PUT/PATCH/DELETE характеристик и их чтение обычными GET товара и списка. Проверьте валидацию и права user/admin.
  6. Проверьте отсутствие документа (null), отключённую Mongo (503) и SQL /health.

В тестовой фикстуре client задайте Mongo URL и отдельную Mongo-базу на каждый тест; после теста удаляйте эту базу. Сравнения GET после L8 дополните attributes: None, если документа нет. SQL-запись возвращает прежний ProductRead.

Дополнительно: добавьте удаление одного ключа через $unset, проверку одновременных первых PUT и сценарий удаления SQL-товара. Объясните, почему SQL rollback не отменяет уже выполненную запись MongoDB.

После L9 товар читается одним HTTP-запросом вместе с характеристиками. PostgreSQL хранит основные данные, MongoDB — attributes; отдельные PUT/PATCH/DELETE меняют только характеристики. JWT и роли остаются прежними.
