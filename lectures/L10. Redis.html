Лекция 10: Redis — кэш характеристик и лимит входа

Познакомимся с Redis: разберём хранение данных в памяти, модель «ключ — значение», основные типы данных и время жизни ключей. Затем подключим его к Products API для кэша характеристик товара и счётчика попыток входа.

Примеры адаптированы к текущему приложению: app/routers/product.py, app/services/product_attributes.py, POST /auth/obtain_token, прежние JWT и роли. Здесь приведены изменения для последовательной реализации; текущий код приложения эта лекция сама не меняет.

Что такое Redis

Redis — серверное хранилище данных, которое работает с данными в оперативной памяти и предоставляет команды для их чтения и изменения. Название раскрывается как Remote Dictionary Server — «удалённый сервер словарей».

Базовая модель — ключ и связанное с ним значение. Приложение знает имя ключа, например products:attributes:42, и запрашивает его значение. При этом Redis поддерживает не только строки, но и структуры данных: словари полей, списки, множества и другие.

Redis используют для кэша, временных состояний, счётчиков и обмена сообщениями. Роль зависит от приложения: в нашей лекции он хранит копии характеристик и счётчики входа. Основные данные товаров продолжают храниться в PostgreSQL и MongoDB.

Введение: Redis Open Source, модель данных и первые команды.

Redis и обычный Python-словарь

Python-словарь dict находится в памяти процесса приложения. Если запустить несколько процессов FastAPI, у каждого будет свой словарь. Значение, записанное одним процессом, само по себе не появится в остальных.

Redis запускается отдельным сервером. Все экземпляры API могут подключаться к нему по сети и работать с общими ключами. Python-библиотека redis-py — клиент этого сервера; redis-cli — клиент для работы из терминала.

FastAPI, процесс 1 ──┐
                    ├── сеть ── Redis Server ── ключи и значения в RAM
FastAPI, процесс 2 ──┘

redis-py  — клиент внутри Python-приложения
redis-cli — клиент в терминале

Поэтому общий счётчик попыток входа можно вынести в Redis. Но сетевой вызов отличается от обращения к локальному dict: у него есть задержка, соединение может оборваться, а сервер — стать недоступным.

Тип выбирают по нужным операциям. В этой практике достаточно String: JSON характеристик сериализуем в строку, а счётчик изменяем через INCR. Redis не разбирает поля JSON, сохранённого обычной командой SET.

Hash Redis и Python dict похожи по назначению, но не идентичны: значения полей Redis Hash не становятся автоматически вложенными Python-объектами.

Память, скорость и кэширование

Redis обслуживает операции над данными в оперативной памяти. Доступ по известному ключу и готовые операции над структурами данных делают его удобным для частых коротких запросов.

Кэширование — сохранение копии результата, чтобы использовать её повторно. Например, API один раз читает характеристики из MongoDB, а следующие запросы некоторое время получают их копию из Redis. Когда копия исчезнет, её можно создать заново из источника.

Цена такого решения — дополнительная память, сетевые обращения и возможность устаревания копии. PostgreSQL и MongoDB тоже используют память для ускорения работы; установка Redis сама по себе не гарантирует более быстрый ответ.

Объём памяти Redis конечен. При настройке maxmemory поведение определяет политика вытеснения: сервер может удалять подходящие ключи или отклонять записи, требующие дополнительной памяти. Поэтому отсутствие ключа — штатная ситуация для кэша.

Подробнее: ограничение памяти и вытеснение ключей.

TTL: время жизни ключа

TTL, Time To Live — оставшееся время жизни ключа. Можно сохранить значение на 30 секунд: после истечения срока ключ считается отсутствующим, и приложение должно быть готово прочитать исходные данные снова.

Сохранили копию attributes с TTL 30 секунд
               ↓
Пока срок не истёк → GET может использовать копию
               ↓
Срок истёк → копии нет → читаем MongoDB и заполняем кэш снова

Срок задают явно: например, SET key value EX 30. Без срока ключ может сохраняться до удаления, перезаписи или вытеснения. TTL автоматически не отслеживает изменения товара в MongoDB: он лишь ограничивает жизнь конкретной копии.

Инвалидация — удаление или признание копии устаревшей после изменения источника. В нашем приложении после записи новых характеристик удалим их Redis-ключ, чтобы следующий GET прочитал MongoDB. Позже разберём, почему даже TTL вместе с удалением не устраняет все гонки.

Атомарные команды и счётчики

Redis предоставляет команды, которые выполняют изменение на стороне сервера. Например, INCR атомарно увеличивает целое значение на единицу: параллельные клиенты не теряют увеличения из-за одновременного чтения старого значения.

Схема GET → вычислить в Python → SET:
клиент A прочитал 3 → записал 4
клиент B прочитал 3 → записал 4
Итог: 4, хотя увеличений было два

Два вызова INCR на сервере:
3 → 4 → 5
Итог: 5

Но несколько отдельных команд не становятся одной атомарной операцией автоматически. Например, между INCR и назначением TTL может оборваться соединение. Для счётчика вместе с TTL используем транзакцию Redis.

Атомарность внутри Redis не объединяет его запись с транзакцией PostgreSQL или изменением MongoDB.

Подробнее: INCR и счётчики.

Сохранение данных Redis на диск

Работа с данными в памяти не означает, что Redis вообще не умеет сохранять их на диск. Для восстановления после перезапуска можно настроить persistence.

МеханизмКак работаетЧто учитывать
RDBСохраняет снимок состояния данных на определённый момент.Изменения после последнего пригодного снимка могут быть потеряны при аварии.
AOFЗаписывает изменения в журнал, из которого можно восстановить данные.Гарантии зависят от настройки записи и синхронизации журнала; сохранение имеет свою стоимость.
Без persistenceДанные остаются только в памяти запущенного сервера.После перезапуска кэш и временные счётчики будут пустыми.

В учебном Compose ниже отключим RDB и AOF: характеристики восстановим из MongoDB, а счётчики входа начнут новое окно. Это выбранная политика нашего приложения, а не обязательное свойство любого Redis.

Если Redis хранит данные, потеря которых недопустима, требования к сохранению и восстановлению нужно определить отдельно.

Применение Redis в приложении

СценарийРешение для этого проекта
Кэш расширенных характеристикОсновная практика: уменьшаем повторные чтения MongoDB в GET товара и списка.
Лимит попыток входаВторая практика: общий для экземпляров API счётчик по IP с коротким TTL.
Кэш всего ответа товараВозможное продолжение: потребуется инвалидировать результат и после SQL-записи, и после записи MongoDB; в кэш попадут цена и остаток.
Отзыв JWT / серверные сессииОтдельная задача. Сейчас активность пользователя проверяется в SQL на каждом запросе; для адресного отзыва JWT понадобятся дополнительные данные токена.
Счётчик просмотров / очередь фоновых задачРасширение при появлении соответствующего API или обработчиков. В текущем каталоге таких сценариев пока нет.

Наша граница кэша — только attributes. Для учебного каталога это компромисс: допускаем короткое устаревание описательных характеристик, а актуальные SQL-поля и проверку прав продолжаем читать из PostgreSQL.

Само подключение Redis не доказывает ускорение: на промахе добавляются сетевые обращения. Полезность проверяем по частоте попаданий, числу Mongo-запросов и времени ответа на своей нагрузке.

За что отвечает каждое хранилище

HTTP → JWT + активный пользователь из SQL → SQL-товар / список
                                               │
                                  id выбранных товаров
                                               ↓
                                  Redis: кэш attributes
                                   │ hit       │ miss
                                   │           ↓
                                   │      MongoDB: attributes
                                   │           │
                                   └─────┬─────┘
                                         ↓
                              ProductWithAttributesRead

PostgreSQL и MongoDB хранят исходные данные. Redis содержит копии характеристик и временные счётчики. Потеря кэша не должна удалять товары, характеристики или пользователей.

GET с попаданием в кэш всё равно обращается к SQL. Он экономит чтение характеристик из MongoDB, но не обходит авторизацию, поиск, фильтры, проверку существования и блокировки пользователя.

Cache-aside: сначала кэш, затем источник

  1. Существующие зависимости проверяют токен и читают SQL-товары.
  2. Одной командой MGET получаем кэш для всех выбранных id.
  3. Для отсутствующих или повреждённых значений выполняем один Mongo-запрос с $in.
  4. Собираем и валидируем ProductWithAttributesRead.
  5. Найденные в MongoDB характеристики кладём в Redis с TTL. Порядок SQL-товаров сохраняется.

Hit — пригодное значение есть в Redis; miss — его нет. Отсутствующий Mongo-документ вернём как attributes: null и в этой практике кэшировать не будем. Поэтому Redis nil всегда означает промах.

Если у списка закэширована только часть характеристик, MongoDB нужна только для оставшихся id. Размер списка по-прежнему ограничен query-параметром limit.

Ключи и TTL

products:attributes:42   → {"attributes":{"layout":"ANSI","wireless":false}}
auth:login:127.0.0.1 → 3

Ключ products:attributes:42 хранит характеристики товара с id=42, а auth:login:127.0.0.1 — число попыток входа с этого IP. Имена задаём прямо в коде. У копии attributes TTL 30 секунд, у счётчика входа — 60 секунд.

Search, category, limit и only_available не входят в ключ характеристики: они выбирают товары в SQL, но не меняют attributes одного и того же товара. Для кэша полного списка эти параметры пришлось бы включить в ключ.

Сейчас товар виден всем активным пользователям одинаково. Если характеристики станут зависеть от пользователя или языка, ключ и границу кэша нужно пересмотреть. Пароли и JWT в кэше не нужны.

Redis в существующем lifespan

Сохраняем lifespan из L9: SQL Engine, создание пользователей и MongoDB остаются на своих местах. Добавляем клиент Redis и его закрытие.

app/core/lifespan.py — добавить импорт.

from redis.asyncio import Redis

В функции появятся три изменения: начальное значение redis_client = None, создание клиента перед yield и await redis_client.aclose() при завершении. Полная функция показана далее, чтобы не потерять существующую очистку MongoDB и SQL.

Lifespan: создание и закрытие клиента

app/core/lifespan.py — заменить только функцию lifespan вместе с декоратором. Остальные импорты и logger из L9 сохраняем.

@asynccontextmanager
async def lifespan(app: FastAPI):
    settings = app.state.settings
    configure_logging()
    logger.info("App starting up...")
    engine = create_database_engine(settings.database_url)
    mongo_client = None
    redis_client = None
    app.state.redis = None
    app.state.engine = engine
    app.state.mongo_database = None
    try:
        if settings.debug:
            with Session(engine) as db:
                seed_users(db, settings)

        if settings.mongodb_url is not None:
            mongo_client = AsyncMongoClient(
                settings.mongodb_url, tz_aware=True,
                serverSelectionTimeoutMS=3000,
            )
            await mongo_client.admin.command("ping")
            database = mongo_client[settings.mongodb_database]
            await ensure_product_attribute_indexes(database)
            app.state.mongo_database = database
        if settings.redis_url is not None:
            redis_client = Redis.from_url(
                settings.redis_url, decode_responses=True,
                socket_connect_timeout=1, socket_timeout=1,
            )
            app.state.redis = redis_client
        yield
    finally:
        try:
            if redis_client is not None:
                await redis_client.aclose()
        finally:
            try:
                if mongo_client is not None:
                    await mongo_client.close()
            finally:
                engine.dispose()
    logger.info("App shutting down...")

from_url создаёт клиент, а соединение будет установлено при первой команде. Отдельный обязательный ping не нужен: Redis здесь необязателен. Ошибки запросов обработаем в функциях кэша и limiter.

Один клиент обслуживает всё приложение. Вложенные finally гарантируют закрытие остальных ресурсов, даже если одно из закрытий завершилось ошибкой. Ошибка запуска MongoDB по-прежнему прерывает запуск, как в L9.

Таймауты ограничивают ожидание одной сетевой попытки; встроенные повторы клиента могут увеличить общее время. Настройку повторов оставляем отдельной темой: таймауты и повторы redis-py.

Зависимость RedisDep

app/dependencies/redis.py — новый файл.

from typing import Annotated

from fastapi import Depends
from redis.asyncio import Redis
from starlette.requests import Request


def get_redis(request: Request) -> Redis | None:
    return request.app.state.redis


RedisDep = Annotated[Redis | None, Depends(get_redis)]

Зависимость возвращает клиент конкретного приложения. Он создаётся один раз внутри lifespan и использует пул соединений. Не создаём Redis на каждый запрос и не берём глобальные settings при импорте.

RedisDep допускает None: это штатный запуск без Redis. MongoDatabaseDep остаётся обязательной для составных GET. Синхронные SQL-зависимости L9 продолжают выполняться в thread pool, асинхронные команды Redis и MongoDB вызываем с await.

Кэш: формат и проверка данных

app/services/attribute_cache.py — новый файл.

import logging

from pydantic import BaseModel, ConfigDict, ValidationError
from redis.asyncio import Redis
from redis.exceptions import RedisError

from app.core.config import Settings
from app.schemas.product_attributes import AttributeKey, AttributeValue

logger = logging.getLogger(__name__)


class CachedAttributes(BaseModel):
    model_config = ConfigDict(allow_inf_nan=False)
    attributes: dict[AttributeKey, AttributeValue]


def attribute_cache_key(product_id: int) -> str:
    return f"products:attributes:{product_id}"

Используем уже знакомый BaseModel. В кэше лежит JSON вида {"attributes": {"layout": "ANSI"}}. Эта же модель проверяет данные и превращает их в JSON для Redis.

allow_inf_nan=False запрещает специальные значения float: inf — положительную бесконечность, -inf — отрицательную бесконечность и nan — «не число». Например, float("inf") и float("nan") не пройдут проверку этой модели: Pydantic выдаст ошибку валидации. Такие значения не предусмотрены стандартным JSON, поэтому числовые характеристики в кэше должны быть конечными. Это проверка Pydantic, а не ограничение самого Redis.

ObjectId и даты остаются в MongoDB. В Redis это обычная строка, модуль RedisJSON не требуется. В модель чтения не переносим лимит 50 ключей: он относится к одному PUT/PATCH, а несколько PATCH могут накопить больше характеристик.

Кэш: пакетное чтение через MGET

app/services/attribute_cache.py — продолжение.

async def read_cached_attributes(
    redis: Redis | None, product_ids: list[int],
) -> dict[int, dict]:
    if redis is None or not product_ids:
        return {}
    keys = [attribute_cache_key(product_id) for product_id in product_ids]
    try:
        values = await redis.mget(keys)
    except RedisError:
        logger.warning("Redis read failed; using MongoDB")
        return {}

    found = {}
    for product_id, raw in zip(product_ids, values):
        if raw is not None:
            try:
                found[product_id] = CachedAttributes.model_validate_json(raw).attributes
            except ValidationError:
                logger.warning("Invalid cache for product %s", product_id)
    return found

Один MGET получает кэш для всех выбранных товаров. Порядок значений соответствует порядку ключей. Нет ключа или JSON не прошёл проверку — прочитаем MongoDB.

Ошибка Redis тоже означает промах. Ошибки MongoDB и SQL не скрываем. Пример рассчитан на один Redis-сервер; ограничения многоключевых операций Redis Cluster — отдельная тема.

Кэш: запись нескольких значений

app/services/attribute_cache.py — продолжение.

async def write_cached_attributes(
    redis: Redis | None, by_id: dict[int, dict], settings: Settings,
) -> None:
    if redis is None or not by_id:
        return
    try:
        async with redis.pipeline(transaction=False) as pipe:
            for product_id, attributes in by_id.items():
                value = CachedAttributes(attributes=attributes).model_dump_json()
                pipe.set(
                    attribute_cache_key(product_id), value,
                    ex=settings.attributes_cache_ttl_seconds,
                )
            await pipe.execute()
    except RedisError:
        logger.warning("Redis fill failed; returning source data")

model_dump_json превращает Pydantic-модель в строку. SET одновременно сохраняет её и задаёт TTL, поэтому отдельный EXPIRE для кэша не требуется.

Pipeline собирает SET-команды и отправляет их пакетом при execute. Вызовы pipe.set не требуют await. Для заполнения кэша общая транзакция не нужна: если сохранилась только часть значений, остальные позже прочитаем из MongoDB.

Ошибка заполнения Redis не отменяет успешное чтение источника. Подробнее: асинхронный pipeline.

Кэш: инвалидация после записи

app/services/attribute_cache.py — продолжение.

async def invalidate_cached_attributes(
    redis: Redis | None, product_id: int,
) -> None:
    if redis is None:
        return
    try:
        await redis.delete(attribute_cache_key(product_id))
    except RedisError:
        logger.warning("Redis invalidation failed for product %s; relying on TTL", product_id)

После успешной записи MongoDB удаляем копию attributes. Следующий GET заполнит её заново. В кэше нет списков: один DEL обновляет и карточку, и все списки, которые содержат этот товар. Поиск ключей по шаблону не нужен.

Если DEL не прошёл, исходная запись уже выполнена. Возвращаем успешный ответ записи, пишем предупреждение и полагаемся на TTL. Это сознательный выбор согласованности для описательных характеристик; общей транзакции MongoDB + Redis нет.

add_attributes: собрать ответ и заполнить кэш

app/services/product_attributes.py — добавить импорты и заменить add_attributes. Ошибки и операции записи L9 сохраняем.

from redis.asyncio import Redis

from app.core.config import Settings
from app.services.attribute_cache import (
    CachedAttributes, read_cached_attributes, write_cached_attributes,
)

async def add_attributes(
    products: list[ProductRead], database: AsyncDatabase,
    redis: Redis | None, settings: Settings,
) -> list[ProductWithAttributesRead]:
    if not products:
        return []
    ids = [product.id for product in products]
    by_id = await read_cached_attributes(redis, ids)
    missing = [product_id for product_id in ids if product_id not in by_id]

    if missing:
        fresh = {}
        cursor = database["product_attributes"].find(
            {"product_id": {"$in": missing}},
            {"_id": 0, "product_id": 1, "attributes": 1},
        )
        async for document in cursor:
            value = CachedAttributes(attributes=document["attributes"])
            fresh[document["product_id"]] = value.attributes
        by_id.update(fresh)
        await write_cached_attributes(redis, fresh, settings)

    return [
        ProductWithAttributesRead(
            **product.model_dump(), attributes=by_id.get(product.id),
        )
        for product in products
    ]

Кэш и MongoDB проверяются одной моделью CachedAttributes. Ошибку документа источника не превращаем в null; повреждённую копию Redis считаем промахом.

Если все значения нашлись в Redis, Mongo-запрос не выполняется. Пустой список не требует сетевых обращений. Отсутствующие Mongo-документы не кэшируем: в ответе будет attributes=null.

Какие изменения требуют инвалидации

ОперацияЧто происходит с кэшем attributes
PUT/PATCH/DELETE /products/{id}/attributesПосле успешной записи MongoDB — DEL одного ключа.
POST /productsКэша списков нет: новый SQL-товар сразу участвует в выборке. Отсутствующие attributes не кэшируем.
PUT/PATCH /products/{id}Цена, наличие, остаток и specs читаются из SQL. Кэш attributes их не содержит.
DELETE /products/{id}SQL-проверка вернёт 404 до чтения кэша; оставшийся ключ истечёт по TTL.
Ручная правка MongoDB вне APIНаш DEL не вызывается: копия может жить до истечения TTL.

Ключи и права должны опираться на серверный id. SQL-id не переиспользуем: после сброса sequence или восстановления только одной базы нужны согласованная очистка и проверка связей. Старый Mongo-документ после SQL DELETE сам не исчезает — это прежнее ограничение L9, кэш его не исправляет.

TTL и DEL не дают строгой согласованности

GET A: miss → прочитал старые attributes из MongoDB
PATCH B: записал новые attributes → DEL кэша → ответил 200
GET A: положил старые attributes в Redis с TTL 30 секунд
GET C: получил старую копию

Удаление после записи не устраняет гонку с уже выполняющимся GET. TTL ограничивает срок жизни конкретной копии с момента её заполнения, а не гарантирует свежесть сразу после PATCH. Не обещаем «не более 30 секунд после изменения»: старый GET мог заполнить кэш позже.

Для описательных характеристик в учебной задаче принимаем такую eventual consistency. Для строгого чтения после записи кэш можно обходить; более сложный вариант потребует протокола версий/условной записи. Один дополнительный DEL или блокировка только внутри процесса полной гарантии не дают.

Кэш цены или остатка потребовал бы отдельного решения о допустимой свежести. В нашей границе эти поля читаются из SQL, без задержки именно из-за Redis.

СитуацияПоведение после этой лекции

MongoDB пропала после запуска; есть пригодный кэшGET может вернуть 200 с SQL-полями и закэшированными attributes.
MongoDB пропала; хотя бы одного нужного документа нет в кэше503 по обработчику L9. Частичный список со скрытой ошибкой не возвращаем.
MONGODB_URL отсутствуетMongoDatabaseDep вернёт 503 и не пустит GET к кэшу: сохраняем явное отключение составного чтения.

Появилась одна новая возможность: тёплый кэш позволяет прочитать характеристики во время сетевого отказа MongoDB. Отсутствующий документ — всё ещё null; отказ источника при miss — 503. /health по-прежнему проверяет только SQL и не является общей readiness-проверкой.

Rate limiting для нашего входа

POST /auth/obtain_token проверяет Argon2-пароль. Для него введём отдельный счётчик: не более 5 корректно сформированных попыток входа с одного IP за окно 60 секунд. Успешные и неуспешные попытки учитываются одинаково.

Лимит применяем до вызова authenticate_user. JWT, OAuth2PasswordRequestForm, username в sub, блокировка пользователя и ответ Token остаются прежними. Лимит не зависит от того, существует ли указанный username.

Используем Redis-счётчик, общий для экземпляров одного окружения. Это не отзыв JWT, не серверная сессия и не блокировка самого пользователя.

Транзакция для счётчика входа

Для limiter достаточно знакомого pipeline, но теперь с transaction=True. Redis выполнит команды одной транзакцией:

  1. INCR увеличит счётчик.
  2. EXPIRE с NX назначит 60 секунд, только если у ключа ещё нет срока.
  3. TTL вернёт оставшееся время для Retry-After.

Последующие попытки не продлевают окно. Между отдельными INCR и EXPIRE больше нет клиентского разрыва. EXPIRE NX поддерживается с Redis 7.0; наш Redis 7.4 подходит.

Это окно от первой попытки, а не скользящий интервал: на границе двух окон возможен всплеск.

Зависимость limiter и ответ 429

app/dependencies/rate_limit.py — продолжение.

async def limit_login_attempts(
    request: Request, redis: RedisDep, settings: SettingsDep,
) -> None:
    if redis is None:
        return
    host = request.client.host if request.client else "unknown"
    key = f"auth:login:{host}"
    try:
        async with redis.pipeline(transaction=True) as pipe:
            pipe.incr(key)
            pipe.expire(key, 60, nx=True)
            pipe.ttl(key)
            attempts, _, ttl = await pipe.execute()
    except RedisError:
        logger.warning("Redis limiter unavailable; allowing password check")
        return
    if attempts > settings.auth_rate_limit_per_minute:
        raise HTTPException(
            status_code=429, detail="Слишком много попыток входа",
            headers={"Retry-After": str(max(1, ttl))},
        )


LoginRateLimitDep = Annotated[None, Depends(limit_login_attempts)]

execute возвращает результаты трёх команд в том же порядке. Нам нужны число попыток и TTL; результат назначения срока пропускаем через переменную _.

После лимита возвращаем 429 и Retry-After. При отказе Redis выполняем обычную проверку пароля и пишем предупреждение. Такой дополнительный limiter не гарантирует защиту при отказе или перезапуске Redis.

Общий IP объединяет пользователей за NAT. За reverse proxy нужно настроить доверенные прокси ASGI-сервера; произвольному X-Forwarded-For из запроса доверять нельзя.

Стоимость и границы решения

  • При полном hit нет Mongo-запроса; SQL-проверки всё равно выполняются. При частичном miss — один Mongo-запрос на выбранные id.
  • На холодном кэше появились MGET и заполнение pipeline. Сравниваем нагрузку и задержки до и после, а не обещаем ускорение по факту установки Redis.
  • TTL не задаёт лимит памяти. Для рабочего Redis отдельно выбирают maxmemory, eviction policy и наблюдают ошибки/попадания. Вытеснение ключа limiter может сбросить счётчик раньше TTL; при строгом лимите кэш и лимиты стоит разделять по ресурсам и политике отказа.
  • Популярный ключ после истечения TTL могут одновременно заполнять несколько GET: это cache stampede. Для небольшой учебной нагрузки допускаем повторы; при необходимости отдельно добавляют координацию и разброс TTL.
  • Транзакция Redis не объединяет его запись с MongoDB или PostgreSQL.

  1. Добавьте Redis к существующему Compose, не меняя SQL/Mongo и их тома.
