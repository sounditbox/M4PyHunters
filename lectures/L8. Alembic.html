Лекция 8: Alembic и переход на PostgreSQL в Docker

В L7 товары и пользователи переехали в SQLModel и SQLite. Теперь научимся менять существующую схему без потери данных: подключим Alembic, создадим начальную ревизию и добавим остаток товара с заполнением старых строк. В конце лекции перенесём проект на PostgreSQL в Docker, чтобы в L9 добавить MongoDB к уже готовой контейнерной инфраструктуре.

Примеры продолжают текущий код проекта. Блоки с пометкой «заменить» заменяют указанный файл; отдельные поля и фрагменты добавляем в существующие классы. Изменения собираем по порядку, сервер запускаем после применения миграций.

Состояние нашего проекта

В проекте уже есть Product(SQLModel, table=True) в app/models/products.py и User в app/models/user.py. Таблицы называются products и users. Поле products.created_by_id связано с users.id; Relationship описывает переход между объектами.

Синхронный Engine создаёт app/db/database.py, SessionDep выдаёт Session на запрос. create_app(settings) сохраняет настройки в app.state.settings. Вход выполняется через POST /auth/obtain_token.

Пока app/core/lifespan.py вызывает SQLModel.metadata.create_all(engine). Это создаёт отсутствующие таблицы, но не добавляет новые поля в существующие таблицы. На этой границе и нужен Alembic.

Проблема: модель изменилась, SQLite-файл остался прежним

Например, старый файл содержит products без created_by_id. Добавление поля в Python-класс не исправит этот файл. ORM начнёт выбирать новую колонку, а SQLite ответит no such column: products.created_by_id.

Миграция — явный шаг изменения схемы и, при необходимости, существующих данных. Код модели описывает нужное состояние, файлы миграций — путь к этому состоянию.

base → 0001: users + products → 0002: stock_count → head

Что делает Alembic с SQLModel

Alembic использует SQLAlchemy metadata. У SQLModel она уже есть: SQLModel.metadata. Создавать собственный DeclarativeBase или переписывать модели на Mapped не требуется.

ЧастьОтветственность
SQLModel.metadataЖелаемые таблицы, колонки, индексы и связи после импорта моделей.
revision --autogenerateСравнить metadata с выбранной БД и записать черновик изменений.
upgrade / downgradeВыполнить прямые / обратные операции из ревизий.
alembic_versionСохранить номер применённой ревизии в самой базе.

Autogenerate не определяет намерение разработчика: переименование может выглядеть как удаление и добавление. Каждый черновик читаем перед применением.

Имена ограничений и регистрация обеих моделей

Для первой истории миграций зададим соглашение об именах ограничений. Важно выполнить его до импорта классов таблиц. Заменяем пока пустой app/models/__init__.py:

app/models/__init__.py — заменить файл

from sqlmodel import SQLModel

SQLModel.metadata.naming_convention = {
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}

from app.models.products import Product  # noqa: E402, F401
from app.models.user import User  # noqa: E402, F401

Теперь импорт пакета регистрирует обе таблицы. Примеры имён: pk_users, ix_users_username, fk_products_created_by_id_users. Для CHECK в этой convention явно задаём name.

Имена в уже существующей БД могут отличаться. Подключение старого файла к истории разберём отдельно: изменение metadata само по себе не переименовывает ограничения в БД.

Настраиваем alembic.ini

В созданном файле меняем секцию [alembic]. Остальные секции, включая настройки logging, оставляем: fileConfig() в env.py их использует.

alembic.ini — изменить секцию

[alembic]
script_location = %(here)s/alembic
prepend_sys_path = %(here)s
path_separator = os

# Удаляем сгенерированную строку sqlalchemy.url = driver://...
# URL возьмём из Settings или из config.attributes.

Строка подключения остаётся в Settings.database_url. Не копируем пароль БД в конфигурацию миграций.

Полный env.py для нашего синхронного Engine

alembic/env.py — заменить файл

from logging.config import fileConfig

from alembic import context
from sqlalchemy import pool
from sqlmodel import SQLModel, create_engine

from app.core.config import get_settings
from app.models import Product, User  # noqa: F401

config = context.config
if config.config_file_name is not None:
    fileConfig(config.config_file_name)

target_metadata = SQLModel.metadata


def get_database_url() -> str:
    # При программном запуске можно передать URL явно.
    url = config.attributes.get("database_url")
    if url is not None:
        return url
    return get_settings().database_url


def run_migrations_offline() -> None:
    url = get_database_url()
    context.configure(
        url=url,
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
        compare_type=True,
        render_as_batch=url.startswith("sqlite"),
    )
    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online() -> None:
    engine = create_engine(get_database_url(), poolclass=pool.NullPool)
    try:
        with engine.connect() as connection:
            context.configure(
                connection=connection,
                target_metadata=target_metadata,
                compare_type=True,
                render_as_batch=connection.dialect.name == "sqlite",
            )
            with context.begin_transaction():
                context.run_migrations()
    finally:
        engine.dispose()


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()

CLI берёт URL из Settings. Через config.attributes URL можно передать программно. Alembic и приложение должны работать с одной БД.

Для metadata импортируем модели, а не app.main. Online подключается к БД и выполняет SQL; offline, выбранный флагом --sql, только выводит SQL-скрипт.

SQLModel-типы в сгенерированных ревизиях

Alembic может вывести строковый тип как sqlmodel.sql.sqltypes.AutoString(length=80). Такой файл должен импортировать sqlmodel. Добавляем импорт в шаблон рядом с SQLAlchemy:

alembic/script.py.mako — дополнить импорты

from alembic import op
import sqlalchemy as sa
import sqlmodel
${imports if imports else ""}

В уже созданной ревизии импорт добавляем вручную. Альтернатива — осознанно заменить AutoString на соответствующий sa.String(length=...). Сам шаблон не исправляет старые файлы.

Первая ревизия: сравниваем с пустой БД

В текущем products.db таблицы уже могут существовать. Генерация начальной миграции против такого файла даст пустой или неполный результат. Для генерации выбираем новый, ещё не существующий файл. Сохраняем командную переменную только в текущем PowerShell:

$env:DATABASE_URL = "sqlite+pysqlite:///./products_migrations.db"
uv run alembic revision --autogenerate --rev-id 0001 -m "create users and products"

Убедитесь, что products_migrations.db действительно новый. В ревизии должны появиться обе таблицы, уникальный индекс логина и FK автора товара. Пока не добавляем stock_count в модели: это следующая ревизия.

Начальная ревизия: проверяем содержимое

Пример полного файла для текущих моделей. Типы и имена проверяем по реальному выводу Alembic; версия генератора может иначе отформатировать код.

alembic/versions/0001_create_users_and_products.py — пример полного файла

from alembic import op
import sqlalchemy as sa
import sqlmodel

revision = "0001"
down_revision = None
branch_labels = None
depends_on = None


def upgrade() -> None:
    op.create_table(
        "users",
        sa.Column("id", sa.Integer(), nullable=False),
        sa.Column("username", sqlmodel.AutoString(length=50), nullable=False),
        sa.Column("hashed_password", sqlmodel.AutoString(), nullable=False),
        sa.Column("role", sqlmodel.AutoString(), nullable=False),
        sa.Column("disabled", sa.Boolean(), nullable=False),
        sa.PrimaryKeyConstraint("id", name=op.f("pk_users")),
    )
    op.create_index(op.f("ix_users_username"), "users", ["username"], unique=True)
    op.create_table(
        "products",
        sa.Column("id", sa.Integer(), nullable=False),
        sa.Column("name", sqlmodel.AutoString(length=80), nullable=False),
        sa.Column("category", sqlmodel.AutoString(length=40), nullable=False),
        sa.Column("price", sa.Float(), nullable=False),
        sa.Column("description", sqlmodel.AutoString(length=500), nullable=True),
        sa.Column("is_available", sa.Boolean(), nullable=False),
        sa.Column("sale_price", sa.Float(), nullable=True),
        sa.Column("specs", sa.JSON(none_as_null=True), nullable=True),
        sa.Column("created_by_id", sa.Integer(), nullable=True),
        sa.ForeignKeyConstraint(
            ["created_by_id"], ["users.id"],
            name=op.f("fk_products_created_by_id_users"),
        ),
        sa.PrimaryKeyConstraint("id", name=op.f("pk_products")),
    )


def downgrade() -> None:
    op.drop_table("products")
    op.drop_index(op.f("ix_users_username"), table_name="users")
    op.drop_table("users")

users создаётся раньше ссылающейся на неё таблицы products. При откате порядок обратный. Relationship не создаёт отдельной колонки: в SQL хранится created_by_id.

Применяем и проверяем историю

uv run alembic check

На новом файле ревизия 0001 создаст таблицы, а в alembic_version появится номер 0001. check должен сообщить, что новых операций нет. Он сравнивает выбранную БД с текущими моделями, а не просто ищет неприменённые файлы.

Миграция создаёт схему. Она не создаёт admin и user: начальные записи по-прежнему добавляет seed_users().

stamp не выполняет DDL и не проверяет схему. Он лишь записывает номер ревизии. Если не хватает created_by_id, stamp это не исправит. Сравниваем существующий файл с чистой БД после 0001; различия имён ограничений также требуют проверки.

Если учебные данные не нужны, можно начать с отдельного нового файла и сохранить старый как копию. Не запускаем первую create_table-ревизию поверх уже существующих таблиц и не помечаем старую схему как head вслепую.

Убираем create_all из lifespan

После применения миграций заменяем файл. Используем существующие функции и настройки проекта; Session factory не вводим.

app/core/lifespan.py — заменить файл

import logging
from contextlib import asynccontextmanager

from fastapi import FastAPI
from sqlmodel import Session

from app.core.logging_conf import configure_logging
from app.db.bootstrap import seed_users
from app.db.database import create_database_engine

logger = logging.getLogger("lifespan")


@asynccontextmanager
async def lifespan(app: FastAPI):
    settings = app.state.settings
    configure_logging()
    logger.info("App starting up...")
    engine = create_database_engine(settings.database_url)
    try:
        app.state.engine = engine
        if settings.debug:
            with Session(engine) as db:
                seed_users(db, settings)
        yield
    finally:
        engine.dispose()
    logger.info("App shutting down...")

Перед запуском API выполняем uv run alembic upgrade head для того же URL. Миграции выполняются отдельной командой один раз на развёртывание, а не каждым worker при старте.

Сохраняем текущую политику проекта: bootstrap запускается только при debug=True. Для чистой БД с DEBUG=False администратора нужно создать отдельной административной командой до входа.

Второе изменение: остаток товара

Добавим stock_count. В проекте таблица Product и схемы API описаны отдельно, поэтому изменяем три места:

# app/models/products.py — поле класса Product
stock_count: int = Field(default=0, ge=0)

# app/schemas/product.py — поле класса ProductBase
stock_count: int = Field(default=0, ge=0)

# app/schemas/product.py — поле класса ProductUpdate
stock_count: int | None = Field(default=None, ge=0)

В файле модели Field уже импортирован из SQLModel; в схемах — из Pydantic. ProductCreate и ProductRead наследуют ProductBase. Сервис PATCH повторно проверяет итоговый ProductCreate, поэтому явный stock_count: null получит 422.

default=0 работает на стороне Python, ge=0 — при валидации. Это не backfill существующих строк и не SQL CHECK. Прямой SQL не получает эти гарантии автоматически.

Генерируем черновик второй ревизии

uv run alembic current
uv run alembic revision --autogenerate --rev-id 0002 -m "add stock count"

Выбранная БД должна быть на 0001. Если сгенерированное add_column(... nullable=False) применить к таблице со строками, новым записям колонок неоткуда взять значение. Исправляем черновик до upgrade.

Backfill: сначала данные, затем NOT NULL

alembic/versions/0002_add_stock_count.py — заменить файл

from alembic import op
import sqlalchemy as sa

revision = "0002"
down_revision = "0001"
branch_labels = None
depends_on = None


def upgrade() -> None:
    op.add_column(
        "products", sa.Column("stock_count", sa.Integer(), nullable=True),
    )
    products = sa.table("products", sa.column("stock_count", sa.Integer()))
    op.get_bind().execute(
        products.update()
        .where(products.c.stock_count.is_(None))
        .values(stock_count=0)
    )
    with op.batch_alter_table("products") as batch:
        batch.alter_column(
            "stock_count", existing_type=sa.Integer(), nullable=False,
        )


def downgrade() -> None:
    with op.batch_alter_table("products") as batch:
        batch.drop_column("stock_count")

Backfill заполняет новое поле у старых товаров. Используем локальное описание sa.table, а не импорт актуальной модели Product: она будет меняться, историческая миграция должна оставаться воспроизводимой.

На время этого учебного перехода запись в API останавливаем. Для приложения без остановки потребовалось бы несколько совместимых этапов развёртывания. Downgrade удалит остатки из БД; это потеря данных, а не восстановление их прошлых значений.

Почему batch mode важен для SQLite

SQLite поддерживает не все изменения через ALTER TABLE. batch_alter_table() при необходимости создаёт временную таблицу нужной структуры, копирует строки, удаляет старую таблицу и переименовывает новую.

render_as_batch=True помогает autogenerate выводить такой код, но не выполняет миграцию и не заполняет данные за нас. На других СУБД тот же batch-блок обычно использует обычный ALTER.

Для нашей синхронной SQLite-конфигурации выполняем online-миграции. Вывод через --sql не всегда работает для batch-пересоздания: без подключения Alembic не может отразить старую структуру таблицы.

Переименование — не удаление поля

Если переименуем description в details, autogenerate может предложить drop + add. Вместо этого используем переименование; это отдельный пример, его не добавляем к упражнению stock_count.

def upgrade() -> None:
    with op.batch_alter_table("products") as batch:
        batch.alter_column(
            "description", new_column_name="details",
            existing_type=sa.String(length=500), existing_nullable=True,
        )


def downgrade() -> None:
    with op.batch_alter_table("products") as batch:
        batch.alter_column(
            "details", new_column_name="description",
            existing_type=sa.String(length=500), existing_nullable=True,
        )

Согласованно меняем модель, схемы и API. Alembic не знает, что два разных имени означают одну и ту же колонку.

Переходим на PostgreSQL в Docker

Теперь сделаем PostgreSQL основной SQL-базой проекта. FastAPI и Alembic пока запускаются локально через uv; в контейнер переносим сервер БД. В L9 добавим в этот же Compose сервис mongo.

Сначала остановите API. Сохраните копию SQLite-файла, с которым прошли миграции, и убедитесь, что он на 0002. Файл остаётся источником для переноса; не удаляем его после переключения URL.

uv add "psycopg[binary]"

SQLAlchemy использует psycopg 3 через диалект postgresql+psycopg. Наш create_database_engine() уже подходит: check_same_thread задаётся только для SQLite.

Compose: сервер PostgreSQL и постоянный том

compose.yaml — новый файл

services:
  postgres:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: products
      POSTGRES_PASSWORD: products
      POSTGRES_DB: products
    ports:
      - "127.0.0.1:5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U products -d products"]
      interval: 3s
      timeout: 3s
      retries: 20

volumes:
  postgres_data:

docker compose up -d --wait postgres
docker compose ps
docker compose exec postgres psql -U products -d products -c "SELECT version();"

В примере используем PostgreSQL 17: его каталог данных монтируем в /var/lib/postgresql/data. Healthcheck и --wait позволяют дождаться готовности сервера, а named volume postgres_data сохраняет данные при пересоздании контейнера.

POSTGRES_USER, POSTGRES_PASSWORD и POSTGRES_DB инициализируют только пустой каталог. Изменение этих значений в Compose не меняет уже созданные роли и базы. Учебные реквизиты задаём прямо в Compose; в .env приложения добавляем только известные поля Settings.

Имя Compose-проекта и путь к compose.yaml сохраняем между L8 и L9, чтобы использовать тот же postgres_data. Обычный docker compose down оставляет том, а down --volumes удаляет данные и не является способом обычного перезапуска.

Переключаем настройки приложения и Alembic

.env — обновить значения, остальные поля оставить

Замените прежнюю строку DATABASE_URL, не добавляйте вторую. DEBUG=True нужен только для нашего локального bootstrap; остальные текущие SECRET_KEY и пароли сохраняем. Такой URL добавляем и в .env.example.

Переменная окружения имеет приоритет над .env, поэтому её важно убрать или явно заменить. И API, и Alembic должны смотреть в один PostgreSQL.

В новой базе повторно применяются 0001 и 0002. Не генерируем новую initial-миграцию и не выполняем stamp на пустой PostgreSQL. Типы и SERIAL для первичных ключей выбирает PostgreSQL-диалект; batch-блок второй ревизии здесь выполняет обычный ALTER.

URL с 127.0.0.1 верен для Python-процессов на компьютере. Внутри другого контейнера понадобился бы хост postgres, имя сервиса Compose, а не localhost. Контейнер API в этих двух лекциях не создаём.

Схема и перенос данных — разные операции

Upgrade создаёт в PostgreSQL таблицы, но не копирует строки из SQLite. До первого запуска API перенесём users и products, сохранив id, хеши паролей, JSON specs и created_by_id.

Если старые данные нужны, выполните скрипт до первого старта API. Обе базы должны быть на 0002, таблицы PostgreSQL — пустыми. Для нового учебного каталога этот шаг можно пропустить.

scripts/copy_sqlite_to_postgres.py — новый файл

import argparse
from pathlib import Path

from sqlalchemy import func, select, text
from sqlalchemy.engine import make_url

from app.core.config import get_settings
from app.db.database import create_database_engine
from app.models import Product, User


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--source-url", required=True)
    args = parser.parse_args()
    source_url = make_url(args.source_url)
    target_url = make_url(get_settings().database_url)
    if source_url.get_backend_name() != "sqlite":
        raise RuntimeError("Источник должен быть SQLite")
    if not source_url.database or not Path(source_url.database).is_file():
        raise RuntimeError("Файл SQLite не найден")
    if target_url.get_backend_name() != "postgresql":
        raise RuntimeError("Назначение должно быть PostgreSQL")

    source_engine = create_database_engine(args.source_url)
    target_engine = create_database_engine(target_url.render_as_string(hide_password=False))
    try:
        with source_engine.connect() as source, target_engine.begin() as target:
            for connection in (source, target):
                versions = connection.execute(
                    text("SELECT version_num FROM alembic_version")
                ).scalars().all()
                if versions != ["0002"]:
                    raise RuntimeError("Обе базы должны быть на ревизии 0002")
            tables = (User.__table__, Product.__table__)
            for table in tables:
                if target.scalar(select(func.count()).select_from(table)):
                    raise RuntimeError("Таблицы PostgreSQL должны быть пустыми")

            for table in tables:
                rows = source.execute(select(table)).mappings().all()
                if rows:
                    target.execute(table.insert(), [dict(row) for row in rows])
                sequence = target.scalar(
                    text("SELECT pg_get_serial_sequence(:table_name, 'id')"),
                    {"table_name": table.name},
                )
                if sequence is None:
                    raise RuntimeError(f"Не найдена sequence таблицы {table.name}")
                last_id = target.scalar(select(func.max(table.c.id)))
                target.execute(
                    text("SELECT setval(CAST(:sequence AS regclass), :value, :called)"),
                    {"sequence": sequence, "value": last_id or 1,
                     "called": last_id is not None},
                )
                print(f"{table.name}: скопировано {len(rows)} строк")
    finally:
        target_engine.dispose()
        source_engine.dispose()


if __name__ == "__main__":
    main()

uv run python -m scripts.copy_sqlite_to_postgres --source-url "sqlite+pysqlite:///./products_migrations.db"

Команду выполняем из корня проекта; в scripts добавляем пустой __init__.py. Если мигрировали другой SQLite-файл, указываем его URL. Скрипт не копирует alembic_version: PostgreSQL уже получил собственную историю через upgrade.

Вставка явных id в PostgreSQL не продвигает sequence автоматически. Поэтому после переноса скрипт выставляет её за максимальный id. Иначе следующий POST мог бы получить уже занятый номер. Данные вставляются в одной транзакции: сначала users, затем products. Скрипт загружает строки в память и подходит для учебного каталога; большой перенос требует отдельного процесса.

Для совершенно нового учебного каталога перенос можно пропустить и наполнить PostgreSQL через API. В этом случае старые SQLite-данные остаются только в сохранённом файле, а локальный seed создаст начальных пользователей при старте.

Практика и критерии готовности

  1. Создайте 0001 на новом файле и проверьте users, products, FK автора, уникальный логин.
  2. Уберите create_all из lifespan. Подготовьте таблицы до запуска API; в debug проверьте вход admin через obtain_token.
  3. Добавьте stock_count в таблицу и схемы, создайте 0002 с backfill. Старые товары должны сохраниться и получить 0.
  4. Выполните check. На отдельной учебной БД проверьте развёртывание с нуля, переход с 0001 на заполненной таблице и откат.
  5. Поднимите PostgreSQL через compose.yaml, переключите Settings и .env, примените существующие ревизии и перенесите учебные данные. Проверьте новый id после переноса.

Дополнительно: добавьте именованный SQL CHECK для неотрицательного stock_count и проверьте отклонение отрицательного значения при прямом INSERT. ge=0 в API эту проверку не заменяет.
